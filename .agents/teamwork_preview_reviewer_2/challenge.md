## Challenge Summary

**Overall risk assessment**: LOW

The proposed modifications to the source management page, uploads page, and wiki expansion are clean, simple, and utilize standard web specifications (such as HTML `<details>` and `<summary>`), reducing risk. However, there are minor assumptions and edge cases around directory naming collisions and DB scalability.

---

## Challenges

### [Low] Challenge 1: Upload ID Naming Collisions

- **Assumption challenged**: Folders directly under a team directory are named exactly after their corresponding `upload_id` generated by the database.
- **Attack scenario**: An editor or an administrator with access to the filesystem (or via manual worker operations) creates a custom folder with a name that is not a UUID but coincidentally matches an `upload_id` from a different team.
- **Blast radius**: The source tree will enrich the node with the timestamp of the matching `upload_id`, displaying incorrect metadata on the `/manage` page.
- **Mitigation**: Filter the `get_all_upload_timestamps` function or the mapping query in `list_sources` to only match uploads belonging to the correct team.

### [Low] Challenge 2: Scalability of Full-Table Fetch

- **Assumption challenged**: The list of uploads in the SQLite database remains relatively small.
- **Attack scenario**: After months of heavy usage, the `uploads` table grows to tens of thousands of records. On every `/api/manage/sources` fetch, a full-table query `SELECT upload_id, created_at FROM uploads` is executed and parsed into memory.
- **Blast radius**: Increased latency on the Manage page, higher CPU/memory usage on the ECS server.
- **Mitigation**: Perform a JOIN/filtering query based on the active directories returned by the worker, or fetch timestamps only for the folders listed on the current page view.

## Stress Test Results

- **Run unit tests under concurrent load** → database lock handles concurrency with RLock and sqlite journal WAL mode → passes safely.
- **Malformed directory names** → `enrich_tree` skips non-string and non-matching folder names → passes safely.

## Unchallenged Areas

- **Worker soft-deletion cleanup logic** — reason not challenged: The filesystem deletion logic remains unchanged on the worker side, which is out of scope for the current UI/metadata review.
